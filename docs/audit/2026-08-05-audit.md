## Phase 2 — Structure & engineering hygiene

### 2.1 Module boundaries — score: 4/5

Imports overwhelmingly respect the ingestion → retrieval → generation → api
direction. Two concrete violations found by exhaustively listing every
`app.*` import in those four packages:

- **Private-symbol reach-across**: `app/generation/advisory.py:32` imports
  `_fold` — an underscore-prefixed, explicitly-internal helper — directly from
  `app/retrieval/product_scope.py:174`, instead of `product_scope.py`
  exposing a public `fold_text()`. A real encapsulation break across the
  generation/retrieval boundary.
- **Backwards pipeline dependency**: `app/ingestion/parsers/
  glossary_parser.py:15` imports `GlossaryEntry`/`load_glossary` from
  `app.retrieval.query_expansion` — ingestion depending on retrieval, which is
  backwards relative to CLAUDE.md's own pipeline ordering. This is
  *deliberate* (the skill explicitly says to reuse the loader so the YAML
  schema is defined once), but the schema/loader arguably belongs in a shared
  module rather than inside `retrieval/` — as written, refactoring
  `query_expansion.py` could silently break ingestion.
- Not flagged as violations: `retrieval/*` importing `ingestion.indexer` for
  the shared Qdrant client (expected, documented); `generation/
  coverage_gate.py` importing `retrieval.coverage.grants_a_benefit` through a
  public function (cross-layer but through a real API, and conceptually
  necessary — the gate re-applies the same benefit test post-generation);
  `chat.py` importing from nearly every retrieval submodule directly, because
  `chat.py` **is** the documented single orchestrator with no separate
  orchestration layer to bypass.

### 2.2 Config discipline — score: 5/5

`grep -rn "os.getenv\|os.environ" app/ scripts/` returns exactly one hit in
all of `app/`, and it is a docstring (`settings.py:4`, describing the rule
itself), zero hits in `scripts/` Python files. Every hit for
`http://|https://|localhost|127.0.0.1` outside `settings.py` is either prose
in an error/comment/docstring or a legitimate fixed constant
(`main.py`'s `_citation_base_is_loopback()`'s definition of what counts as
loopback, used to validate a setting, not bypass one). `scripts/open_webui/*`
carries its own hardcoded local defaults, but that code runs inside the
separately-installed Open WebUI process and cannot import `app.config.
settings` — a reasonable, bounded exception. **Zero real config-discipline
violations found in `app/`** — this is the cleanest section of the audit.

### 2.3 The guard stack — traced order, from `chat_completions` → `plan_response` → `_retrieve` → generation

| # | Guard / stage | Effect |
|---|---|---|
| 1 | Confirmation resolver (`chat.py:151`) | Rewrites query to the original question when a spellcheck confirmation was just answered |
| 2 | Meta-task detector (`chat.py:101`) | **Block** — Open WebUI title/tag requests short-circuit before any RAG work |
| 3 | Spellcheck/typo gate (`spellcheck.py`, called `chat.py:387`) | **Block** — asks for confirmation, no retrieval run |
| 4 | Advisory follow-up label carry-over (`chat.py:179`) | Annotate, computed from the **raw** query |
| 5 | Conversation scope (`conversation_scope.py::active_scope`) | Biases the rewrite and later scope filter |
| 6 | Standalone rewrite (`query_rewrite.py::rewrite_standalone`) | **Rewrites** query into `standalone_query` |
| 7 | Coverage-thread detection (`chat.py:270-272`) | Annotate — mixed basis: thread-check on raw query, question-check on standalone query, OR'd together |
| 8 | Multi-product routing vs. single-product search+rerank | Branches the whole retrieval strategy |
| 9 | Metric guard (`metric_guard.py`) | **Filters** fee/interest hits on benefit-payout queries |
| 10 | Product-scope guard (`product_scope.py`) | **Block** — refuses if the named product is absent from every retrieved doc |
| 11 | Hybrid/refusal fallback | **Block** — refuses or falls back to labeled general-knowledge mode on zero hits |
| 12 | Advisory routing (`advisory.py::is_advisory_query`) | Annotate — selects prompt variant |
| 13 | Coverage backfill (`coverage.py::backfill_payout_clause`) | **Rewrites context** — a second `hybrid_search` fetches a benefit clause if none is present |
| 14 | Coverage reorder (`coverage.py::payout_clauses_first`) | Benefit clauses moved to rank 1 |
| 15 | Prompt assembly + history sanitize (`history.py`) | Strips our own appended suffixes from prior assistant turns before replay |
| 16 | Generation | Calls Ollama; **blocks gracefully** on connection failure |
| 17 | Coverage verdict gate (coverage turns only, `coverage_gate.py`) | **Regenerates once**, then replaces with a deterministic enumeration if still ungrounded |
| 18 | Semantic verifier (coverage turns only, `verify.py`) | **Regenerates once** more; fails open on any HTTP error |
| 19 | Suffix assembly | Appends disclaimers + sources block in a fixed order |

Three concrete findings from tracing this by hand (not from docs):

**(a) Load-bearing ordering, undocumented.** The multi-vs-single-product
routing decision (`chat.py:246-248`) is computed from the **raw** query,
while the later single-product scope filter (`chat.py:197-221`) checks
product labels against the **rewritten** `standalone_query`. If history-based
rewriting adds or drops a product name, these two decisions can disagree, and
nothing in the code comments this as a known tension.

**(b) A guard that silently no-ops without logging.** `app/retrieval/
retriever.py:76-78` — `hybrid_search` returns `[]` with **no log line**
whenever the Qdrant collection doesn't exist yet (a fresh embedded-Qdrant
directory before first ingest, or a name mismatch after a config change).
Every other empty/disabled-guard path in the codebase logs something
(glossary load failure, every guard's own enable/disable, warmup failures) —
this is the one silent exception, and downstream it's indistinguishable from
"genuinely zero matches," which makes a fresh or misconfigured deployment
harder to diagnose than it needs to be.

**(c) Potentially contradictory effect, partially self-aware.** The coverage
flag at `chat.py:270-272` OR's a thread-check on the raw query with a
question-check on the rewritten query — a comment justifies using the raw
query for the thread-check specifically ("opening turn carries the marker...
follow-ups do not"), but doesn't address the mixed-basis OR as a whole, so a
rewrite that changes topic could still produce a coverage flag that doesn't
match what actually gets searched for.

### 2.4 Error handling

| Failure | Caught? | User sees |
|---|---|---|
| Ollama connection failure/timeout (streaming or not) | **Yes** — `generator.py:473-477` / `:774-776` | Graceful Vietnamese message: *"Xin lỗi, hiện không thể kết nối tới mô hình sinh câu trả lời. Vui lòng thử lại sau."* |
| Qdrant lock contention **at startup** (warmup) | Yes, best-effort — `main.py:56-63` logs a warning, app still starts | Graceful (nothing user-visible breaks) |
| Qdrant lock contention **on a live request** (not warmup) | **No** — `indexer.py`'s `get_client()` and `retriever.py`'s `hybrid_search` have no try/except around the Qdrant call | Raw, unhandled 500, generic English FastAPI error, no Vietnamese message |
| Parser exception mid-ingest | **Partially** — only `NotImplementedError`/`ValueError` are caught (`ingest.py:208-213`) and mapped to a 415 (whose message is English, per the doc-drift note above). Any other exception type — a `pypandoc` crash on a corrupt `.docx`, Docling raising mid-convert on a malformed PDF, a Qdrant upsert error — is **not caught** | Raw, unhandled 500 for anything outside those two exception types |
| Exception during rerank | **No** — `reranker.py::rerank` has no try/except around `score_fn(...)` (ultimately `FlagReranker.compute_score`) | Raw, unhandled 500 (model-load failure, OOM, tokenizer error all propagate) |

**Summary**: the generation layer is uniformly defensive and Vietnamese on
failure — genuinely good, careful work (the same "fail open with a logged
warning" pattern shows up consistently in `verify.py` and `enrichment.py` for
`httpx.HTTPError`). The retrieval layer (Qdrant queries, reranker inference)
and most of the ingestion parser layer have **no exception handling at all** —
a real inconsistency against the otherwise-careful "never leak a raw error"
posture visible everywhere else in the codebase.

### 2.5 Testability — 5 biggest gaps

1. **`app/retrieval/retriever.py::hybrid_search`** has zero direct test
   coverage — `tests/test_retrieval.py`'s own docstring states it needs no
   live services, and confirmed by grep, the file never calls `hybrid_search`
   at all (only the pure `rrf_fuse` helper is tested). Fix: give it an
   injectable `client` parameter, mirroring the seam `reranker.rerank`
   already has via `score_fn`.
2. **`generator.py`'s actual Ollama HTTP call paths** (`_stream_chat`,
   `_chat_raw`, `_achat_raw`) are untested — `test_generation.py` states "No
   Ollama needed" and only imports pure helpers. No mock-transport usage
   exists anywhere in the suite. This means the one error-handling path
   confirmed most defensive (§2.4's Ollama-failure row) has **no regression
   test** protecting it.
3. **`docx_parser.py::parse_docx`** — zero test coverage of any kind; no
   `.docx` fixture exists anywhere in the repo, and no test file references
   it. The one real (non-stub) parser with no test at all.
4. **Real model-loading/inference paths** — `indexer.py::get_embedder`/
   `embed_texts` and `reranker.py::get_reranker`/`_flag_rerank_scores` (the
   real bge-m3/bge-reranker-v2-m3 calls) are never exercised in `pytest`; only
   pure downstream logic with an injected `score_fn` is tested. A version
   bump or API-shape change in `FlagEmbedding` would only surface at runtime.
5. **`ingest.py::_run_pipeline`'s non-`NotImplementedError`/`ValueError`
   exception paths** are untested — the 415-only except clause is the only
   thing between a malformed upload and a raw 500, and its own gaps (§2.4)
   aren't covered.

A genuine positive: `tests/conftest.py` has an autouse fixture that
monkeypatches `product_scope._load_indexed_titles`/
`comparison._load_indexed_docs` to `[]` specifically so the suite never
depends on embedded-Qdrant state — a real, deliberate testing seam, alongside
clean examples like PDF parsing being tested via a `_convert_with_docling`
monkeypatch.

### 2.6 Dependency health

Four `requirements*.txt` files split by install phase; `scripts/
setup_native.sh` installs `requirements.txt` + `requirements-embed.txt` +
`requirements-pdf.txt` only — **`requirements-ml.txt` (`paddleocr`,
`paddlepaddle`, `ragas`) is never installed by the native (canonical)
deployment path**, correctly, since none of those three are needed by
anything currently reachable. Every line across all four files is exactly
pinned (`==`); the sole documented exception is `torch`/`torchvision`,
deliberately unpinned here and installed separately from the PyTorch CPU

## Phase 3 — Backend: security & maintainability

*(Produced by a dedicated verification pass reading every file cited below in
full; see `2026-08-05-metrics.md` for the agent methodology note.)*

### 3.1 Authentication / authorization

There is exactly one auth mechanism, and it does not cover the endpoint
employees actually call.

- `app/auth.py:33-92`: a single shared admin password
  (`settings.admin_password`, empty by default) gates a session cookie
  (`bv_admin_session`), HMAC-signed with a 12h TTL. No per-employee identity —
  `auth.py:1-8` states this explicitly ("not a multi-user account system").
- Enforcement is one FastAPI middleware, `app/main.py:117-132`
  (`admin_session_gate`), applied to every route except `auth.is_public_path`
  (`app/auth.py:87-92`): `/login`, `/logout`, `/health`, `/v1/*`
  (`PUBLIC_PREFIXES`), and `GET /documents/{doc_id}/(view|file)`.
- **When `ADMIN_PASSWORD` is unset (the shipped `.env.example` default), the
  gate is a full no-op for every route.** `main.py:81-85` logs a startup
  warning but does not block. Confirmed live in `logs/api.log`. With the
  default empty password, anyone who can reach the port can upload, list,
  edit, and delete every document via `POST /ingest` /
  `GET/PATCH/DELETE /documents...`.
- **`POST /v1/chat/completions` and `GET /v1/models` are ALWAYS public at the
  FastAPI layer**, regardless of `ADMIN_PASSWORD` — `/v1` is unconditionally
  in `PUBLIC_PREFIXES`. The only auth on this path is Open WebUI's own
  `WEBUI_AUTH`, a *different process*. Anyone reaching the FastAPI port
  directly (curl, Postman) bypasses Open WebUI's login entirely.
- **`GET /documents/{doc_id}/view` and `/file` are unconditionally public by
  design** (so citation links work without a session) — and `doc_id` is not a
  secret: `uuid5(_DOC_NAMESPACE, filename)` with a hardcoded public namespace
  UUID (`app/api/ingest.py:37-46`). Anyone who knows or guesses a filename can
  compute its `doc_id` offline and fetch the full document, no session needed.

**Per-department access control on retrieval: confirmed absent.** `department`
is a real field threaded through `ParsedDocument` → `Chunk` → `QdrantPayload`
(`app/models/schemas.py:80,114,169`), validated at upload
(`app/api/ingest.py:49-69`) — but it is **only ever written and displayed**,
never read by `retriever.py`, `chat.py`, or any guard (confirmed by grep for
`department` across `app/`). `ChatCompletionRequest` carries no identity field
at all. **Answer: yes — today, one employee's query can retrieve another
department's document chunks**, because there is no concept of "the
requesting employee's department" anywhere in the request path.

### 3.2 Upload path (`app/api/ingest.py`)

- **File-type validation**: extension-based only (`router.py:35-64`); no
  magic-byte or `Content-Type` check.
- **Size limits**: none. No `MAX_UPLOAD`-style setting exists; upload is fully
  buffered via `await file.read()` before any check, with no size cap.
- **Path traversal**: correctly mitigated — `_safe_filename`
  (`ingest.py:97-108`) reduces to the final path component only.
- **Zip/XML bomb exposure (DOCX/XLSX)**: no guard. `pypandoc.convert_file` and
  `openpyxl.load_workbook` run directly on uploaded files with no
  entity-expansion or decompressed-size cap — fully trusts library defaults.
- **Temp-file cleanup: files are never deleted, on any path** — including
  failed/malformed uploads, which persist forever, unindexed and orphaned
  (`dest.write_bytes(...)` happens before the `try` block that handles known
  parse failures; other exceptions propagate as a raw 500 with the file still
  on disk).
- **Disk permissions**: uploads directory created with `mkdir(parents=True,
  exist_ok=True)`, no `mode=` argument — OS default umask only.

### 3.3 Prompt injection

- **Chunk text never reaches the system-role message** — confirmed by reading
  `build_messages`/`build_user_prompt` (`generator.py`, `prompts.py`): context
  is always appended in the user turn, never the system turn.
- **Citation numbers cannot be forged by document content** — `[n]` is
  assigned purely by loop position over `hits`, never derived from chunk text.
  But **there is no runtime check that a generated answer's `[n]` markers
  actually resolve** before the answer reaches the employee — the
  dangling-citation check (`eval/run_ragas.py`) is an offline eval metric
  only, not wired into `chat_completions`.
- **The coverage gate trusts raw document text as ground truth with only
  keyword matching** — `grants_a_benefit` (`app/retrieval/coverage.py:183-195`)
  is a substring match against a small fixed marker list, applied to whatever
  text was ingested. A chunk containing a stray phrase like "Công ty chi trả"
  out of context can satisfy the gate; a real clause phrased without any fixed
  marker is invisible to it. This requires upload access (gated when
  `ADMIN_PASSWORD` is set), but is a genuine gate-gaming vector on a
  security-relevant classification with no semantic check.
- **No delimiting of retrieved context** — nothing fences chunk text as "data,
  not instructions" beyond the general system-prompt rule to answer only from
  context.

**Proposed mitigations**: (1) a runtime dangling-citation check in
`chat.py`/`generator.py`, not just in eval; (2) explicit fencing of each `[n]`
context block as data; (3) a structural (not pure-substring) check backing
`grants_a_benefit`/`metric_guard`'s marker lists.

### 3.4 Output safety

- **No unsafe HTML rendering found.** `app/static/index.html`'s three
  `innerHTML` writes all pass every dynamic value through `escapeHtml()`; the
  streamed chat answer uses `.textContent`, not `innerHTML`.
- `app/api/docview.py` (the citation-link viewer) uses `MarkdownIt(... {"html":
  False, "linkify": False})` and separately `html.escape()`s math spans —
  self-contained, XSS-safe by construction, matching its own docstring claim.
- **`_validate_source_url`** (`app/api/ingest.py:72-94`): http(s)-scheme-only
  regex, no host allowlist. Any `https://` URL is accepted for a knowledge-pack
  citation — a malicious upload could point "(nguồn công khai)" at a
  look-alike phishing domain. The app never fetches it (consistent with the
  air-gap rule), so this is a social-engineering risk for the clicking
  employee, not a runtime exfiltration risk.

### 3.5 Secrets & PII

- `.gitignore` correctly covers `data/*`, `.env`, `/models/`,

  `git ls-files` cross-check confirms only the two intended glossary/manifest

- **`eval/golden_set_reference.json` is untracked but NOT covered by

### 3.8 Maintainability — new-document-type / new-guard walkthrough

### 3.10 Observability — top finding

`app/query_timing.py` deliberately records only counts/lengths/timings, never
query text, answer text, retrieved chunk IDs, scores, or the exact prompt sent
to Ollama (confirmed live: `logs/query_timings.jsonl` has exactly one line,

extending the existing JSONL record with per-hit `doc_id`/`section_path`/score
would not require logging any document content, resolving the tension with
the project's own no-content-logging stance.

### 4.5 Recommendation — Open WebUI vs. a custom frontend

**Recommendation: keep Open WebUI for chat, and extend the existing
`app/static/index.html` admin surface with analytics — do not build a third,
unified custom frontend. This is not a close call.**

Reasoning:
1. The chat experience Open WebUI provides today — SSE streaming, KaTeX math
   rendering, chat history, and (per Open WebUI's own native feature set) a
   thumbs-up/down feedback mechanism not yet wired to this app — represents
   weeks of frontend work if rebuilt from scratch, and it is already branded,
   working, and Vietnamese-localized (§4.1). There is no admin-dashboard
   requirement that touches the *chat* surface; Phase 6's admin wishlist is
   entirely about corpus/usage/quality analytics, which is a different screen
   for a different user (the manager, not the employee).
2. The project has *already* made the right architectural call once:
   `app/static/index.html` is a deliberate, dependency-free, air-gap-safe
   vanilla HTML/CSS/JS admin page built specifically because "Open WebUI has
   no notion of our custom `/ingest` endpoint" (`app/main.py:7-10`, its own
   docstring). The correct extension of that decision is to keep growing
   *that* surface with analytics views, not to introduce a second competing
   frontend pattern (e.g. a React/Vue build step) that would need its own
   build tooling, its own air-gap review, and its own maintenance story on a
   Docker-free company laptop.
3. A single unified "pane of glass" (EVALUATION.md's 4.1 UX gap) is a real,
   valid critique, but low severity relative to what actually blocks
   management from getting value this week: there is no usage or quality data
   to *show* on any pane yet (Phase 3.10, Phase 6). Chasing a unified frontend
   before there is data to unify would be visible effort with no analytical
   payoff — instrumentation has to come first regardless of which frontend
   hosts the eventual charts.

**Effort estimate**:
- *Extend `app/static/index.html` with analytics* (recommended): a few hours
  per new view (a "Chất lượng" tab reading an aggregated `query_timings.jsonl`
  summary; a "Sử dụng" tab once per-department/session data exists) using the
  same vanilla-JS/fetch pattern already proven in the file. Low risk — it's
  the same file, same stack, same air-gap posture; a new `<section class=
  "card">` block is additive, not a rewrite.
- *Build a unified custom frontend replacing both surfaces*: multiple weeks —
  re-implementing SSE streaming, KaTeX, chat history, and Open WebUI's native
  feedback mechanism is the majority of that cost, not the admin CRUD (which
  already exists and is small). High regression risk to a chat experience
  that currently works well. **Not recommended for this project's timeline or
  team size (one developer).**

## Phase 6 — Persona A: the admin who deploys (non-engineer)

Role-play: I am the Bảo Việt Life manager who ran `scripts/run_native.sh` on
my work laptop, uploaded a folder of policy PDFs, and now want to know the
system is working and where employees are getting stuck. I cannot read Python.

### What I have TODAY (verified against `app/static/index.html`, live
`GET /documents`, and `logs/`)

Upload (drag-drop, doc_type/department/title/source_url), a table of indexed
documents (title/type/department/chunk count/ingest date) with a clickable
document viewer, edit (rename/re-type/re-department/source_url — a rename
warns it will re-ingest), delete (with confirmation), health badges for
Ollama/Qdrant polled every 15s, a raw-LaTeX "quick ask" smoke-test box, and a
login/logout flow (only active when `ADMIN_PASSWORD` is set — off by default).
This is a genuinely complete CRUD surface, confirmed in Phase 4.

### What I need that does NOT exist yet

**Corpus view** — parse failures / OCR-confidence flags: NO SOURCE (OCR
doesn't exist yet, so there's nothing to flag against). Docs that produced
zero retrievals ever: NO SOURCE (nothing joins query hits to doc identity over
time — this is the same gap as ADM1). Chunk counts/ingest date: EXISTS today.

**Usage analytics** — questions/day, active users, peak hours,
per-department volume, session length, follow-up rate: NO SOURCE.
`logs/query_timings.jsonl` has no user/department/session identity at all
(deliberately — see below), and while Open WebUI's own `webui.db` likely has
per-user chat history, nothing in this repo reads it. Requires new
instrumentation or a new webui.db integration — not free.

**Quality analytics** — the "Tôi không tìm thấy thông tin" (refusal) rate:
PARTIALLY AVAILABLE — computable today from `query_timings.jsonl`'s `mode`
field with a small script, just not surfaced anywhere. Coverage-gate
trigger/regeneration rate: NO SOURCE as a queryable metric (only free-text log
lines in `logs/api.log`). Citation resolution rate: NO SOURCE at runtime
(only computed offline against the golden set). Thumbs-up/down: DOES NOT
EXIST — Open WebUI has a native feedback UI, but nothing in this API captures
or aggregates it. **This is a confirmed, concrete gap** worth calling out on
its own: the single cheapest, highest-signal quality metric a non-technical
manager could watch (👍/👎 rate) has a free UI already sitting there, unused.

**Retrieval analytics** — most-retrieved documents/sections, top queries,
queries that retrieved nothing, unmatched glossary terms: NO SOURCE, and this
one is a **deliberate trade-off, not an oversight** — `query_timing.py`'s own
docstring states it deliberately excludes query/answer text and hit identity
for privacy. Building this dashboard means a real product decision (what to
log, for how long, who can see it), not a silent instrumentation fix — flagged
for a decision point in the roadmap, not assumed away.

**Performance** — latency p50/p95 over time: PARTIALLY AVAILABLE (the raw
numbers are in the JSONL log already, just not aggregated/rendered anywhere).
Tokens/sec, model in use: static, no live switching. Queue depth: NO SOURCE
(no concurrency instrumentation exists, consistent with MAINT4's finding that
the process-wide lock has no depth counter).

**Operational controls** — re-index a document: EXISTS. View a document's
chunks: EXISTS (`/documents/{id}/view`, confirmed well-built in Phase 4).
**View a conversation with its retrieved context (audit trail): DOES NOT
EXIST** — this is exactly ADM1, the top observability finding, restated from
the admin's own point of view: I have no way to pull up "what did the system
actually see" for a question an employee flagged as wrong. Export a report
for management: DOES NOT EXIST. Health status of ollama/qdrant/disk: PARTIAL
(disk space is never checked).

### Feasible in one week vs. needs instrumentation first

**Feasible now** (data already exists, just needs a view): a static
"operations" report reading `logs/query_timings.jsonl` — refusal rate over
time, `elapsed_ms` p50/p95, mode breakdown, hit-count distribution. This is a
report generator over data that already exists, realistically a day or two of
work extending the existing `app/static/index.html` pattern (per Phase 4's
recommendation).

**Needs new instrumentation first** (cannot be charted until collected, per
the audit's own ordering rule): the query/answer-level audit trail (chunk
ids+scores+context_text — ADM1, the highest-value gap, since it also fixes
the "can't reconstruct a bad answer" problem); per-department usage
(blocked on there being no request-level identity at all, not just a UI gap);
thumbs-up/down capture (needs a small new endpoint plus Open WebUI feedback
wiring); coverage-gate counters as structured fields rather than free-text
log lines.

**Explicitly not proposed**: logging raw question/answer text by default.
CLAUDE.md's no-telemetry rule and `query_timing.py`'s own stated privacy
stance argue against it, and this section deliberately scopes every
instrumentation proposal above to metadata (chunk IDs, scores, counts, mode
labels) rather than content — the same design boundary the codebase has
already drawn for itself.

### Deliberate design decisions considered and NOT flagged

- **Embedded Qdrant, single-process, Docker-free deployment.** CLAUDE.md
  states this is mandatory ("company machines don't allow Docker"). The
  single-process constraint this creates (eval must stop the API first) is a
  real operational cost, but it is the direct, necessary consequence of a
  requirement this audit was told to treat as fixed, not a design flaw to
  relitigate.
- **`coverage_gate.py` making coverage turns non-streaming.** CLAUDE.md
  documents this explicitly, with dated incident evidence (2026-07-27, a real
  4-turn conversation that denied a covered claim 4/4 times even with the
  benefit clause backfilled and ranked first). The audit's own Phase 5/6
  stress-tests this decision (see below) rather than re-arguing it in the
  abstract.
- **Parent-child chunking.** Shipped, measured (EVALUATION.md's own A/B), and
  directly documented in CLAUDE.md with its rationale. Not re-litigated.
- **`history.py` stripping our own appended suffixes before replay.**
  Directly documented in CLAUDE.md with a dated incident (three source blocks
  in one answer by turn 4). Not re-litigated.
- **`query_timing.py` never logging question/answer text.** This audit
  considered recommending full query/answer logging as the fix for ADM1
  (observability) and deliberately did NOT — CLAUDE.md's no-telemetry rule and
  the module's own stated privacy stance argue against it. ADM1's proposed fix
  (chunk IDs + scores + guard flags, not content) was chosen specifically to
  respect this existing decision rather than override it.
- **Docker Compose parity gaps (M15-M18 in Phase 3.11).** These are real and
  confirmed still open, but CLAUDE.md explicitly frames Docker as "an optional
  dev-machine stack," not the deployment target. This audit considered
  ranking them as high-severity structural findings and chose not to — a
  never-deployed path drifting from the deployed path is a lower-stakes
  problem than anything on the native path, and is reflected in Phase 7's
  table as low severity / no-longer-urgent rather than omitted.
- **A small local (7-8B) chat model never trusted for arithmetic (the
  mandatory calc disclaimer).** Directly documented, deliberate, and
  independently sensible given the deployment constraints (no cloud model
  available). Not flagged.
- **The LLM-as-judge being replaced by deterministic `must_say`/`must_not_say`
  assertions as the actual eval gate.** This is *already* the project's own
  fix (Phase 3.3/`d016193`) for a real problem (the judge scored a wrong,
  unsafe answer as correct in every stored run) — not a new finding, and not
  something to re-flag as broken.
